MUNIComb  /  SDK

Build on the mesh.
Without guessing.

Add a button to a stock tool, tap it, a job runs on the network, and the result returns to the spot where the button was pressed. The button is only a client. The network stays behind the API.

That split is the whole point: your tool stays yours, the network stays the network, and work is tracked and verified, not taken on trust.

What the SDK will be, when it is ready

  • A port and endpoint map — where services listen, so developers and AI agents do not hand-guess ports or endpoints. The map is verified against actual services before it is claimed live for SDK use, and re-verified before anyone codes against it. Never type a port from memory.
  • Endpoints + auth — how to get in, how a key is issued, revoked, and rate-limited. Status: OPEN.
  • A job envelope — what you send in, what comes back, and a full error when something fails, never a generic error. Status: DESIGN-ONLY, not proved by a real job yet.
  • A catalog of job types — what jobs actually exist, and which are proven, not just designed. The SDK catalog must match the proven catalog, not copy a claim from it. Status: OPEN.
  • Examples and a hello-world — one working job, with the same output shape in test and in real use. A hello-world is proven only by a real job, not by a snippet that was never run. Status: OPEN.
  • Pay and credits — how a job is priced, and how to check a payout. Status: OPEN, gate not cleared. No token, no charge by this draft.
  • Verification — how to prove a result, and how a failed job fails loudly, with credit released, never stuck forever. Status: DESIGNED, NOT SDK-PROVEN.
  • Retries, timeouts, and dedup — so a retry does not double-pay or double-play. Status: OPEN.
  • Machine-readable docs — so agentic developers can write to the network API without hand-rolling every call. Status: OPEN, placeholder only.
  • Versioning and a changelog — what changed, what is deprecated, and what replaces it. Scheme proposed below, no version published yet.
  • A clear agreement boundary — what is open, what stays behind the API, and what must be disclosed. Status: OPEN, review owed before lock-in. This page is not legal advice.

Status words, used everywhere in SDK docs, with no other meanings: PROVEN = record + job proof, Ken-gated. DESIGN-ONLY = design finished, no real job proof yet. OPEN = not designed, not proven, or gate not cleared. DEPRECATED = was proven, superseded, with replacement named, and kept in the changelog, never silently deleted.

What “proven” means

Proven means exactly this, nothing looser: a job type, endpoint, example, or recipe is proven only if there is a Wyatt record for it and a tracked job proof behind it — the job ran, with what input, what output and hash, whether it verified, and whether it paid where pay applies. Anything without both stays marked open or design-only, even if the design is finished on paper.

Recommended code in the SDK can therefore be checked against the network, not just trusted from a doc.

How it will stay current — living docs, not a second memory

Wyatt is the historical record — once merged, it is corrected by a new record on top, never silently edited. SDK docs are the living current reference — when an API changes, a port moves, or a new job type is proven, the SDK docs change with it, in place, with a version and a changelog entry.

Otherwise a developer codes against a stale network, and the failure looks like their bug, not ours.

Dynamic tag design — proposed, not built, not a decision to build a generator yet. In plain words: a Wyatt record carries a structured tag for its SDK category, status, job proof, Wyatt record, and first appearance. The SDK table for that category is pulled from merged Wyatt records by those tags, on the next generation. When a new API lands in a merged Wyatt record, with the right tag, it shows up in the SDK table. When a port moves, the tagged port record changes, and the SDK table changes with it.

  • Only merged Wyatt main feeds the SDK. An open PR, a draft, or a local note does not, no matter how good it looks.
  • A tag alone does not make something proven. Proven still needs a record + job proof. A tagged design stays design-only until that proof lands.
  • Every generated SDK table records the Wyatt main SHA it was pulled from, so a reader knows exactly which snapshot they are coding against.
  • A generated table never claims an item ready that its source record marks open or design-only. Status travels with the item.
  • The generator never pulls secrets, keys, or key material into SDK docs, even if tagged.
  • Agreement / license items and pay / token-shaped items do not auto-feed on a tag alone. They need a human gate in addition: review before lock-in, and counsel + credits-first gate for anything token-shaped, even if tagged.

Retro-tagging existing Wyatt files, vs tagging forward only, is still open and must be decided — this page does not retro-tag anything by itself.

Versioning — proposed scheme

  • SDK version starts at 0.1.0 for the first gated draft, not 1.0. 1.0 is reserved for a gated, proven hello-world + envelope + catalog + auth + pay + verification set, not for a draft.
  • Each SDK release records: version, date, Wyatt main SHA generated from, list of items added / changed / deprecated, and Ken gate reference for each gated item.
  • A deprecated item stays in the changelog with its replacement. It is not silently deleted from SDK docs a developer may already be coding against.

Ready means — unchanged from the plan

The SDK is ready only when: the port table is verified against actual services, the envelope + catalog + hello-world are proven by a real job, auth + pay + verification are checked live, and Ken gates the list item by item — not when this draft, or any list, is written.

By that test, the SDK is not ready as of this draft. Port table is the furthest along, and even it is not yet added to Wyatt main as a record. Everything else is open or design-only, as marked above.

What this draft does NOT do

  • No code build, no SDK client code, no machine-readable server build.
  • No SDK publish, public or private, and no public documentation site launch.
  • No company formation, no merchant, no token, no charge, no pay change.
  • No claim that any endpoint, job type, price, or verification method on this page is ready, proven, or live for SDK use, beyond the status markings above.
