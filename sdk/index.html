Build on the mesh.
Without guessing.

Add a button to a stock tool, tap it, a job runs on the network, and the result returns to the spot where the button was pressed. The button is only a client. The network stays behind the API.

That split is the whole point: your tool stays yours, the network stays the network, and work is tracked and verified, not taken on trust.

What the SDK will be, when it is ready

  • A port and endpoint map — where services listen, so developers and AI agents do not hand-guess ports or endpoints.
  • Endpoints + auth — how to get in, how a key is issued, revoked, and rate-limited.
  • A job envelope — what you send in, what comes back, and a full error when something fails, never a generic error.
  • A catalog of job types — what jobs actually exist, and which are proven, not just designed.
  • Examples and a hello-world — one working job, with the same output shape in test and in real use.
  • Pay and credits — how a job is priced, and how to check a payout.
  • Verification — how to prove a result, and how a failed job fails loudly, with credit released, never stuck forever.
  • Retries, timeouts, and dedup — so a retry does not double-pay or double-play.
  • Machine-readable docs — so agentic developers can write to the network API without hand-rolling every call.
  • Versioning and a changelog — what changed, what is deprecated, and what replaces it.
  • A clear agreement boundary — what is open, what stays behind the API, and what must be disclosed.

Status now — draft, not ready

SDK plan draft v1 is on record in Wyatt (PR #34 merged 2026-10-29, main 8a434799), built off the SDK readiness list in that same record. By that record's own test, the SDK is not ready:

  • Port table is the furthest along, and is still being verified against actual services before it is claimed live for SDK use.
  • Everything else is open or design-only, as marked in the draft.
  • No SDK client code, no public documentation site, and no launch is authorized by this draft alone.

Ready means: the port table is verified, the envelope + catalog + hello-world are proven by a real job, auth + pay + verification are checked live, and each item is gated item by item — not when a list or a draft is written.

How it will stay current

Wyatt is the historical record — once merged, it is corrected by a new record on top, never silently edited. SDK docs are the living current reference — when an API changes, a port moves, or a new job type is proven, the SDK docs change with it, in place, with a version and a changelog entry.

Otherwise a developer codes against a stale network, and the failure looks like their bug, not ours.

Only merged, gated records feed the SDK. A draft, an open proposal, or a local note does not, no matter how good it looks. A tag alone does not make something proven — proven still needs a record and a job proof behind it.
